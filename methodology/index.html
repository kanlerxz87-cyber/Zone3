Methodology & automation architecture

The eight-stage pipeline, the per-row verification protocol, the scalability properties of a static build, and an explicit list of what this analysis cannot claim.

Data as of: 2026-11-13 Verification: every row cites an official source or is flagged 24 open flags

Architecture

Five stages, each with an explicit input contract and an explicit failure mode. A stage never substitutes a value it did not receive; it emits a blank and raises a flag.

01 INTAKE submitted link → extract id → length/format rule (SRC-08) 02 VERIFICATION /dp/ probe + redirect trace + control probe → accept | reject+flag 03 ENRICHMENT Creators API GetItems/GetVariations/GetBrowseNodes → evidence pack 04 ANALYSIS niche_score, price & review features, ranking 05 GENERATION template + claim grounding (every sentence bound to a field) 06 GATE verify_site.py: disclosure? disclaimer? source per row? links? 07 PUBLISH static build → GitHub Pages (24h cache ceiling respected) 08 FEEDBACK earnings report import → EPC re-rank (static sub-tags only) On any blocked input: field := null, flag := FLG-nnn, pipeline continues.

Stage 01–02: intake and verification

The identifier is validated before anything reads it, then probed directly at /dp/<id>, and a known-good ASIN is probed as a control in the same run so a tooling fault can never masquerade as a product finding. This is the stage that rejected all three submissions.

Stage 03: enrichment

Only Creators API (four operations) and Amazon-served links are admissible sources for product facts. No image storage; ≤24h cache for other Program Content; ASINs storable indefinitely. Rate limits and the 40KB payload ceiling are enforced client-side.

Stage 04: analysis

Niche scoring, price-band features and review aggregates. Weights are declared and version-controlled so a ranking change is auditable, and every derived metric is labelled as derived on the page that shows it.

Stage 05–06: generation and gate

Templates plus a per-claim evidence binding; then a hard gate. The gate checks that every table row cites a source or carries an unverified flag, that every source and flag id resolves, that both required disclaimers are present, and that no internal link 404s. The build in front of you passed that gate — the gate is the deliverable as much as the pages are.

Stage 07–08: publish and feedback

Static output means no runtime dependency on Amazon, which keeps the site inside the caching rules by construction. The optimisation loop closes from the monthly Earnings Report, not from a scraping job — the only input that carries authoritative order and revenue numbers.

Verification protocol applied to every row of this site

  1. Primary source only. amazon.com, affiliate-program.amazon.com, sell.amazon.com and ftc.gov. Third-party blogs and search snippets were excluded even where they agreed with the primary text.
  2. Read, not recalled. Each clause was fetched from the live page in this session; the observed text is recorded in the source register so a reader can compare it.
  3. Negative results are results. A 404, a sign-in redirect and a deprecation notice are each recorded as findings with the URL that produced them.
  4. Blanks over guesses. 36 product cells and every per-category rate are blank because no official source exists for them here.
  5. Control test. Every probe is run against a known-good input in the same session, to prove the negative was real.
  6. Machine-checked. verify_site.py re-reads the emitted HTML and fails on a row with no source, a dangling flag, a missing disclosure, or a broken internal link.

Scalability properties

  • Adding a product is one row in data/products.json — no page code changes, no new template.
  • Output is O(products × templates) static files; no server, no database, and no runtime call to Amazon.
  • The cache ceiling becomes a build cadence, not an invalidation system: rebuild within 24h or the price block is withheld.
  • The gate scales for free — 30 tables pass the same rule check as 3, because the rule is per-row in the renderer.
  • Multi-marketplace is a config change: marketplace id, TLD and locale per site, with the same four API operations.

Known limits of this analysis

  • No product facts for the three submitted items — the site therefore demonstrates the system, not a market read.
  • Per-category commission rates were not retrievable without an authenticated account, so no revenue projection is offered.
  • No live campaign data exists, so EPC, CVR and click figures are unpopulated by definition.
  • Niche rankings are withheld rather than approximated; the fixture used to unit-test the scorer is never published.
  • Amazon's rules and API surface move without notice; this analysis is dated 2026-11-13 and is scheduled for quarterly re-verification.
